# Mock Data Generation — Virginia Analytics Tables

Generates realistic, fully synthetic CSV data for local development, API
testing, dashboard testing, and demos — per issue [#301](https://github.com/saayam-for-all/data/issues/301).

No real or sensitive user information is used anywhere in this data. All
names, emails, phone numbers, and addresses are generated by [Faker](https://faker.readthedocs.io/).


(Python 3.10+, standard library `csv`/`argparse`/`random` otherwise.)

## How to Run

From this directory:

```bash
python generate_mock_data.py
```

This generates all 10 CSVs into the current directory using the defaults
(400 users, 100 organizations, seed 42).

### Configuring Row Counts

```bash
python generate_mock_data.py --users 1000 --orgs 250 --seed 7
```

| Flag | Default | Purpose |
|---|---|---|
| `--users` | 400 | Number of `users` rows to generate |
| `--volunteer-fraction` | 0.5 | Fraction of users who also get `volunteer_details` (and downstream `user_skills`/`volunteer_locations`) rows |
| `--orgs` | 100 | Number of `organizations` rows to generate |
| `--seed` | 42 | Random seed — same seed always produces the same output, for reviewable PR diffs |
| `--outdir` | `.` | Directory to write CSVs to |

`countries` (10), `states` (15 US states), `cities` (~45, a few per
state), and `help_categories` (15) are a small curated reference set and
are not scaled by `--users`/`--orgs` — they represent lookup/reference
data, not high-cardinality transactional data. Increase the lists in
`utils.py` (`COUNTRIES`, `US_STATES`, `STATE_CITIES`, `HELP_CATEGORIES`)
if a larger reference set is needed later; the generation logic does not
need to change.

## Table Relationships

```
countries (10)
    |
    v
states (15, all under United States)
    |
    +--> cities (~45; curr_loc/prev_loc columns derive from these coords)
    |
    +--> users (N)
            |
            +--> volunteer_details (N * volunteer_fraction)
            |        |
            |        +--> user_skills (references help_categories.cat_id)
            |        |
            |        +--> volunteer_locations (references volunteer_details.user_id)
            |
            +--> user_locations (references users.user_id directly)

help_categories (15) <--- user_skills.cat_id

states <--- organizations.state_id
```

Key points (see issue #301 for the full list):
- `volunteer_locations.user_id` references **`volunteer_details.user_id`**,
  not `users.user_id` directly — every volunteer-location row's user
  first has a `volunteer_details` row.
- `user_locations.user_id` references **`users.user_id`** directly.
- `volunteer_locations`/`user_locations` don't store `city_id`/`state_id` —
  they store `prev_loc`/`curr_loc` as WKT points (`POINT(lon lat)`,
  loadable into `geography(Point, 4326)` via `ST_GeogFromText`), jittered
  around the user's assigned city so geography stays plausible.
- `users.last_location` is a native Postgres `point` (not geography),
  written as `(lon,lat)`.
- `states.country_id` is `NOT NULL` — every state row references a real
  country row.

## Validation

The script validates itself on every run and exits non-zero if any check
fails:

- No duplicate primary keys in any table
- No orphan `country_id`, `state_id`, `user_id`, or `cat_id` foreign keys
- `volunteer_locations.user_id` always exists in `volunteer_details`
- `organizations.state_id` always exists in `states`

If you change the generation logic, re-run the script — validation runs
automatically before any CSV is written.

### Manual spot-checks before opening a PR

- [ ] CSV headers match the current schema (see the wiki link above)
- [ ] Row counts match what you passed via `--users`/`--orgs`
- [ ] `created_at <= last_updated_at` holds wherever both columns exist
- [ ] No real names/emails/phones/addresses appear (should be impossible —
      everything is Faker-generated — but worth a quick `grep` if you
      hand-edit anything)
- [ ] CSVs load cleanly into a local Postgres instance with the current
      schema (`\copy <table> FROM '<file>.csv' WITH CSV HEADER`)

## Notes / Assumptions

- `country_id`/`city_id` are simple sequential integers assigned during
  generation (not the production sequence-generator IDs, since those are
  DB-side).
- `user_id` and `org_id` mimic the production ID format
  (`SID-00-XXX-XXX-XXX-XXX-XXX`, `ORG-XXX-XXX-XXX-XXXX`) so downstream
  code that parses these formats keeps working against mock data.
- `user_status_id` is weighted toward `1` (assumed "Active") since most
  matching/testing scenarios need mostly-active users; adjust the weights
  in `gen_users()` if a different status distribution is needed.
- Reusable/idempotent: re-running with the same `--seed` reproduces
  identical output, which keeps PR diffs meaningful if the script is
  tweaked later.
